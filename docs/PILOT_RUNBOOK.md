# Pilot runbook (phase 1)

What changed, how to switch it on, and the daily operations for the 30-day paid pilot.

## What changed

| Area | Before | Now |
|---|---|---|
| Scoring | One prompt; the model picked the score | The model reports evidence; code verifies quotes and computes marks (`supabase/functions/_shared/scoring.ts`) |
| Rubrics | Same generic 40/25/20/15 split for every question | Per-question rubric (`question_rubrics` table), falling back to key points |
| Non-answers | Charged and scored | Rejected free of charge (fewer than 30 words, gibberish, repetition) |
| Who writes scores | The browser (anyone could insert any score) | Only the `evaluate-answer` function, with the service role |
| Edge functions | `verify_jwt = false`, no auth check: anyone could run up the Azure bill | Signed-in users only |
| Progress-report email | Anyone could send any user's report to any address | Own report, own address only (or a service-role scheduled job) |
| Answer photos | Public bucket | Private bucket |
| Credits | None | 1 free evaluation, then packs via Razorpay payment links |
| Recurring weaknesses | None | "Your recurring gaps" on the dashboard after 3 answers |
| Video, audio, leaderboard, streak freeze | On | Off (turn back on with `VITE_FEATURE_*=true`) |

## How an evaluation runs

1. The browser calls `evaluate-answer`. It checks the answer, takes one credit and saves the submission as a **queued** job. It responds at once (202).
2. The same function scores the job in the background. The browser watches its row over Realtime (polling every 4 s as a fallback) and shows the result when the row becomes **evaluated**.
3. If scoring fails (AI provider down, timeout), the job goes back to **queued** with a backoff of 30 s, then 2 min. The `evaluation-worker` function picks it up; pg_cron calls it once a minute, only when work is waiting.
4. After 3 failed attempts the job is marked **failed** and the credit is refunded automatically. A job whose worker died is reclaimed when its 3-minute lock expires.

Check the queue: `select * from evaluation_queue_stats;` and, for one job, `select status, attempts, last_error, next_attempt_at from answer_submissions where id = '...';`

The scheduler needs three Vault secrets per environment: `project_url`, `anon_key` (public) and `evaluation_worker_secret` (generated by the migration).

## Switch it on

1. **Apply the migration** `supabase/migrations/20261121160000_phase1_pilot_readiness.sql` (`supabase db push`, or let Lovable apply it on sync, then confirm in the dashboard that `question_rubrics`, `evaluation_credits` and `credit_ledger` exist).
2. **Deploy all edge functions** and set the AI secrets listed in `.env.example`. `config.toml` has `verify_jwt = true` for every function.
3. **Make yourself an admin:** `insert into user_roles (user_id, role) select id, 'admin' from auth.users where email = 'you@example.com';`
4. **Create the payment links** in Razorpay (₹99 / ₹199 / ₹499) and set `VITE_PAYMENT_LINK_5`, `VITE_PAYMENT_LINK_10` and `VITE_PAYMENT_LINK_30` in the frontend env (see `.env.example`). Packs without a link are hidden.
5. **Load rubrics** (see `rubrics/README.md`). The three in the repo are drafts; nothing uses them until a mentor marks them reviewed.

Old submissions keep working. Photos uploaded before the change were saved as public URLs; they stop loading once the bucket is private, which is intended.

## CI/CD

`.github/workflows/ci.yml` runs on every pull request and every push to `main`:

| Job | What it checks |
|---|---|
| App | typecheck, app tests (`npm run test:ci`), database tests on PGlite (`npm run test:sql`), rubric files, production build |
| Edge functions | Deno end-to-end tests for evaluation, OCR, payments and privacy; type-check of every deployed function |
| Migrations plan | (PRs) which migrations would be applied to production, as a dry run |
| Deploy | (push to `main`, after both checks pass) `supabase db push`, then deploy the 12 live edge functions |

Render deploys the web app from `main` only after these checks pass (`autoDeployTrigger: checksPass` in `render.yaml`).

Run everything locally before pushing: `npm run verify` (needs Deno 2 for the edge tests).

**One-time setup:** GitHub repo → Settings → Secrets and variables → Actions → *New repository secret*:
- `SUPABASE_ACCESS_TOKEN`: supabase.com → Account → Access Tokens → *Generate new token*.
- `SUPABASE_DB_URL`: Supabase dashboard → *Connect* → **Session pooler** → copy the URI and put your database
  password in it (Project Settings → Database → *Reset database password* if you don't know it). The direct
  address is IPv6-only, which GitHub's runners can't reach.

Without these, the checks still run and the deploy job is skipped with a warning.

**Protect main:** Settings → Branches → Add rule for `main` → *Require status checks to pass*: select
**App (typecheck, tests, build)** and **Edge functions (Deno end-to-end)**.

**Quarantined tests:** 13 older test files were already failing before the pilot work; they're listed in
`vitest.ci.config.ts` and skipped in CI. Fix one, remove it from the list, and CI starts enforcing it.

**Changing the database:** add a new file `supabase/migrations/<YYYYMMDDHHMMSS>_<name>.sql` (never edit one
that's already applied), add a test in `tests/sql/`, open a PR. The *Migrations plan* job shows it; merging
applies it.

  verification on → Google Account → App passwords → create one. SMTP host `smtp.gmail.com`, port `465`,
  user = the Gmail address, password = the app password, sender = the same address. Fine for the pilot

## Legal pages and privacy (DPDP Act)

Public pages: `/about` (with pricing), `/terms`, `/privacy`, `/refunds`, `/delivery` (also `/shipping`), `/contact`.
They're linked from the landing page, the sign-in page and the app sidebar. These are the pages Razorpay asks for
when activating live mode.

**Before Razorpay live mode:** set the `VITE_LEGAL_*` variables on Render (Dashboard → shastralab-1694 →
Environment), then redeploy. Until they're set, the pages show a "Draft" banner and placeholders. Use the same
legal name, address and phone that you give Razorpay at KYC. Have a lawyer read the Terms and Privacy Policy before
a public launch; they're written for this product, but they aren't legal advice.

**What's built in:**
- *Consent:* sign-up requires a checkbox (18+, Terms, Privacy, AI processing); the record lands in `user_consents`.
  Google users, and everyone after a policy change, see a one-time prompt in the app.
  To change a policy: edit the page, bump `POLICY_VERSIONS` in `src/config/legal.ts`, deploy.
- *Access:* Settings → Your data → Download (all tables, as JSON).
- *Erasure:* Settings → Delete account (type your email to confirm). Removes answer photos and the account; every
  user table cascades. Payment records stay, detached from the person, for tax law.
- *AI providers:* OpenRouter requests carry `provider.data_collection = "deny"`, so they're only routed to providers
  that don't train on or store prompts. If a free model has no such provider, the request falls back to the next
  provider. In the Groq console, turn on *Zero Data Retention* (Settings → Data Controls).

**Requests by email** (from the address on the account):

```sql
-- correction, e.g. name
update profiles set full_name = 'New Name' where email = 'aspirant@example.com';
-- who agreed to what
select * from user_consents where user_id = (select id from auth.users where email = 'aspirant@example.com');
```

Respond to grievances within 90 days at most (DPDP Rules); aim for 2 working days.

**Still to do for full DPDP compliance by 13 May 2027:** a written breach-response plan (who notifies users and the
Data Protection Board, and within what time); a yearly check that the processors listed in the Privacy Policy are
still the real ones; the 3-year inactive-account cleanup the Privacy Policy promises (a scheduled job, plus an email
30 days before).

## Photo and scanned-PDF reading limits

Reading photos and scanned pages costs AI quota but no credit, so each user gets
`OCR_DAILY_PAGE_LIMIT` reads per day (default 40, resets at midnight India time; admins exempt).
A page that fails to read is given back. The app sends a scanned PDF one page per request,
so long PDFs never time out; if the limit runs out midway, the pages already read are kept.

See today's heaviest users:

```sql
select u.email, o.pages from ocr_usage o join auth.users u on u.id = o.user_id
where o.day = ocr_today() order by o.pages desc limit 20;
```

## Payments (Razorpay Orders, automatic)

Students pick a pack in the app → Razorpay Checkout (UPI, card, netbanking) → credits land instantly.
The price comes from `credit_packs`, never from the browser. Every order is credited exactly once:
the browser confirms it (`verify-payment`) and Razorpay's webhook confirms it too, in case the tab closed.

**Switch on (test mode first):**
1. Razorpay Dashboard → *Test mode* → Account & Settings → API Keys → generate. In Supabase → Edge Functions → Secrets add
   `RAZORPAY_KEY_ID` (`rzp_test_…`) and `RAZORPAY_KEY_SECRET`.
2. Dashboard → Webhooks → Add: URL `https://xcrlxcyicagthchxasgx.supabase.co/functions/v1/razorpay-webhook`,
   choose a long random secret, events **payment.captured, order.paid, payment.failed, refund.processed**.
   Add the same secret as `RAZORPAY_WEBHOOK_SECRET`.
3. Buy a pack on the site with test card 4111 1111 1111 1111 (any future date, any CVV) or UPI `success@razorpay`.
4. Going live: complete KYC, switch to *Live mode*, generate live keys + a live webhook, replace the three secrets.

Until the keys are set, the buy dialog falls back to the old payment links (`VITE_PAYMENT_LINK_*`).

**Prices:** `update credit_packs set price_paise = 14900 where id = 'standard';` (paise; ₹149). Hide a pack with `active = false`.

**Refunds:** refund in the Razorpay dashboard. The webhook takes back the matching share of credits
(all of them for a full refund), but never credits already used.

**Checks:**

```sql
-- today's sales
select pack_id, count(*), sum(amount_paise)/100 as rupees from payment_orders
where status = 'paid' and paid_at > now() - interval '1 day' group by 1;
-- anything Razorpay sent that we did not credit (should be empty)
select received_at, event, order_id, outcome from payment_events
where outcome in ('amount_mismatch', 'unknown_order') order by received_at desc;
-- paid at Razorpay but unpaid here: compare with Dashboard → Payments
select * from payment_orders where status = 'created' and created_at < now() - interval '1 hour';
```

**Manual credit** (goodwill, or a payment link from before Orders):

```sql
select grant_credits('aspirant@example.com', 10, 'pay_XXXXXXXX', '₹199 pack');
```

Re-running with the same payment id does nothing. History: `select * from credit_ledger where user_id = (select id from auth.users where email = '...') order by created_at desc;`

## Calibration (before launch, then weekly)

1. Collect 100 real answers: `answers.csv` with `item_id,question_id,answer_text`.
2. Have 2-3 mains-qualified evaluators score each one independently: `human.csv` with `item_id,rater,score,max_marks`.
3. Score them with the evaluator (admin token, no credits used, nothing saved):
   ```bash
   SUPABASE_URL=... SUPABASE_ANON_KEY=... ADMIN_ACCESS_TOKEN=<admin JWT> \
     npm run calibrate -- run --answers answers.csv --out ai.csv
   npm run calibrate -- report --human human.csv --ai ai.csv --json report.json
   ```
4. Target: **at least 70% within ±1.5 marks on 10-markers (±2.3 on 15-markers)** of the human average. The report also shows how often the humans agree with each other, which is the realistic ceiling, plus systematic bias and the worst disagreements. Fix the rubrics behind the worst items first.
